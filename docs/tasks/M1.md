## Remaining limits after the deep audit

New or restated limits; none of them has a task yet.

- Unix cleanup walks the process tree. A daemon that detached before the walk, or one the user cannot inspect, can survive; every such run is labelled `descendants`. There is no cgroup or kernel-level containment.
- On Linux, Landlock cannot hide reads, so a confined process can read Kaisa's state (label `state-read`).
- A legacy attempt (made before owner locks) is never cleaned automatically; a person runs the printed `git worktree remove`, and the next `kaisa` start records it as reclaimed.
- Kaisa processes do not share a single ledger writer. Appends use immediate transactions with a busy timeout, so concurrent goals wait instead of failing (`concurrent_owners_append_every_event_to_one_intact_hash_chain`), and owner locks stop one process from reclaiming another's live attempt.
- A child's environment is an allow-list. A check that needs another variable sees it unset; a custom Codex provider needs `KAISA_PASS_ENV`.
- Tamper detection is lexical. Script flags spelled another way, `.github/actions/**` and CI systems not on the list are not caught.
- Trusted checks and the first settings scan read the repository's working tree, not the base revision.
- The T16.0 and `--confine-claude` runs, and the keychain exception for confined Claude, were not repeated with a real agent after the state-isolation fixes.
- Codex attempts showed no cost in `watch` in the real run (usage is recorded, price is not converted).
