## (c) 문서·목표와 실제의 차이

`verification-quality`의 0.95 truth threshold, `verify rollback --last-good`, dashboard 설명을 기본 런타임 보장으로 해석하면 안 된다. 스킬 자체가 일부 design임을 명시한다. 실제 `ruflo verify`는 signed witness의 설치 파일 hash/marker 검사이며 생성 코드 테스트나 자동 rollback이 아니다. 심지어 `allOk`는 signature와 regressedCount만 검사하여 missingCount와 driftCount를 실패 조건에 넣지 않는다. 근거: `.agents/skills/verification-quality/SKILL.md:17`, `:22`, `:296`; `C/src/commands/verify.ts:217`, `:231`, `:250`.

## Kaisa에 가져올 아이디어와 피해야 할 점

가져올 것은 **권한 gate, 독립 verifier evidence, 학습 eligibility, 사용자 delivery를 서로 다른 상태 전이로 명시하는 설계**다. Ruflo의 policy receipt와 edit 이후 exit-status/taint 판정은 참고할 만하다. Kaisa에서는 immutable source digest에 test·security·review evidence를 묶고, 최종 delivery 직전 단일 gate가 필수 evidence와 최신성을 확인하도록 설계하는 편이 좋다. 이는 Ruflo의 현재 보장이 아니라 위 결손에서 도출한 제안이다(`C/src/mcp-client.ts:276`; `M/hooks/loop/record.ts:114`). 피할 것은 success boolean/exit 0을 품질 합격으로 읽기, 추천 도구를 집행기로 부르기, unsigned/unknown과 검증됨을 섞기, 검증 실패를 삼킨 채 성공처럼 보고하기다(`C/src/mcp-tools/hooks-tools.ts:1888`; `X/src/dual-mode/orchestrator.ts:273`; `M/hooks/trust.ts:177`).
